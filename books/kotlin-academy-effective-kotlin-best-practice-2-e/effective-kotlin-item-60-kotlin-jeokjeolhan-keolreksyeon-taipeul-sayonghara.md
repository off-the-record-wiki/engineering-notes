# (Effective Kotlin Item 60) Kotlin - 적절한 컬렉션 타입을 사용하라

#### 적절한 컬렉션 타입을 사용하라

* `List`, `Set` 그리고 `Map`은 인터페이스로 표시된다. 각각의 인터페이스별로 특정한 규약이 있다.
  * `List`는 순서가 지정된 요소 모음을 나타낸다. 동일한 요소가 여러 번 나타날 수 있다. `List`의 요소는 인덱스를 통해 조회할 수 있다.
  * `Set`는 컬렉션을 이루는 요소들이 고유한 값을 가진다.
  * `Map`은 키-값 쌍 집합을 나타낸다. 각 키는 고유해야 하며, 정확히 하나의 값을 가리켜야 한다.
* 위와 같은 규약이 있더라도 각각의 컬렉션을 다양한 방식으로 구현할 수 있다. 각각의 구현 방식을 비교하면 다음과 같은 차이점이 있다.
  * 연산의 효율성에 영향을 미치는 내부 데이터 구조
  * 컬렉션의 가변성 여부, 변경 가능하다면 쓰레드 안전(Thread-Safe)한지 여부
* 코틀린에서 사용되는 대부분의 컬렉션은 내부적으로 변경 가능하므로 쓰레드 안전하지 않다.

#### 배열 기반 리스트

* 코틀린의 `List`는 내부적으로 배열을 사용해서 구현되었다.
* 따라서 `List`는 배열을 래핑한 것으로 볼 수 있으며, 배열은 일정한 크기의 메모리 공간을 배열의 크기만큼 연속으로 메모리에 할당한 것이다.
* 배열을 사용하여 구현된 `List`는 실제 가지고 있는 요소의 개수와 배열의 크기를 알 수 있다.
* 요소의 개수가 배열의 크기와 동일해지면 배열은 더 큰 규모의 배열로 교체된다. `ArrayList`가 규모를 늘리는 방식은 이전 배열 크기에 특정 인수를 곱한 크기로 새로운 배열을 만드는 것이다. `ArrayList`가 작아지는 방식은 배열의 크기는 그대로 둔 채, 제외된 요소를 `null`로 대체하는 것이다.
* `ArrayList`의 작동 방식을 이해하고 나면 각각의 연산을 수행할 때, 시간이 얼마나 오래 걸릴지 예상할 수 있으며 작업 복잡도 또한 계산이 가능하다.

#### 덱

* 덱(Double ended queue)은 양방향으로 요소를 추가하거나 제거할 수 있는 큐를 나타낸다.
* 코틀린은 `ArrayDeque`로 덱을 제공하고 있으며, `ArrayDeque`는 `MutableList<E>` 인터페이스를 구현하고 있다.
* 동작은 `ArrayList`와 유사하지만 내부 배열이 원형 배열이라는 차이점이 있다. 따라서 컬렉션의 첫 번째 요소가 배열의 시작점이 아닐 수 있으며, `head`라는 별도의 프로퍼티를 두어 컬렉션의 첫 번째 요소를 참조한다.
* 따라서 내부 배열의 공간에 여유가 있는 경우 시작 부분이나 끝 부분에 요소를 추가 또는 제거하는 것은 배열에 요소를 추가하고 `head`만 변경하면 되기 때문에 시간 복잡도가 O(1)이 된다.
* 하지만 배열이 가득 차게 되면 새로운 배열을 만들어 전체 요소들을 이동시켜야 하기 때문에 선형 복잡도를 가진다.
* 스택이나 FILO를 구현할 때 `ArrayList`를 사용하는 것이 좋다. FIFO와 같은 큐를 구현할 경우 `ArrayDeque`가 좋은 선택이다.

#### 연결 리스트

* 배열을 사용하는 리스트 대신 연결 리스트를 사용할 수 있다.
* 연결 리스트는 노드로 구성된 데이터 구조이며, 각각의 노드는 값과 다음 노드에 대한 참조로 구성된다.
* 리스트의 마지막 노드는 `null`을 참조한다. 리스트는 첫 번째 노드를 조회할 수 있도록 참조하고 있다.

```kotlin
/** 값 하나 + 다음 노드 참조. */
class Node<T>(val value: T, var next: Node<T>? = null)

class LinkedList<T> : Iterable<T> {

    private var head: Node<T>? = null

    // ...
}
```

* 연결 리스트의 가장 큰 장점은 위치와 관계없이 요소를 추가하거나 제거하는 연산의 시간 복잡도가 상수(O(1))라는 것이다. 단지 참조하는 대상만 변경하면 된다.
* 요소를 추가하는 연산은 항상 빠르며, 리스트의 초기 크기를 설정할 필요도 없다. 연결 리스트의 가장 큰 단점은 특정 인덱스로 요소를 조회하는 연산의 시간 복잡도가 선형(O(N))이라는 점이다. 요소의 시작점부터 인덱스에 해당하는 요소까지 리스트를 순회할 수밖에 없기 때문이다.
* 요소를 추가 또는 제거하는 연산을 수행할 때 요소들을 이동시키지 않아도 되지만, 인덱스에 해당하는 위치를 찾기 위해 리스트를 순회해야 하므로 결국 선형 복잡도(O(N))를 가진다.
* 연결 리스트는 값과 함께 다음 요소를 참조해야 하기 때문에 공간을 두 배 차지한다. 연결 리스트가 요소 검색, 요소 변경, 리스트 순회를 수행할 때 걸리는 시간 복잡도는 배열 리스트와 똑같이 선형(O(N))이다.

#### 해시 테이블

* 컬렉션에서 값을 빠르게 조회할 때 해시 테이블을 사용한다.
* 해시 테이블의 기본 형태에서는 요소의 순서가 유지된다. 요소의 순서를 유지하기 위해 코틀린의 `Set`와 `Map`에서는 해시 테이블과 연결 리스트를 사용하고 있다. 해시 테이블의 각 요소는 `LinkedList`의 노드이다. 따라서 `Set`, `Map`에는 순서와 관련된 규약이 없음에도, 코틀린의 `Set`와 `Map`은 요소가 추가된 순서를 알 수 있다.
* `Set`, `Map`에서 요소의 순서가 중요하지 않다면 연결 리스트를 사용하지 않아도 된다. 연결 리스트를 만들고 유지하는 데 비용이 많이 들기 때문에 연결 리스트를 사용하지 않으면 메모리가 절약되고 처리 속도도 빨라진다.

#### 정렬된 이진트리

* Kotlin에서는 `sortedSetOf` 및 `sortedMapOf` 함수를 사용해 정렬된 세트 또는 정렬된 맵을 만들 수 있다.
* 요소를 특정 순서로 유지해야 하는 컬렉션이 필요할 때 사용할 수 있다.
* 정렬된 세트와 정렬된 맵에서 요소를 조회하는 연산의 시간 복잡도는 O(log N)이므로 배열 리스트보다 좋지만 해시 테이블보다는 나쁘다.
* 요소를 추가하고 제거하는 연산 또한 요소의 위치를 먼저 찾아야 하기 때문에 시간 복잡도가 O(log N)이다. 트리를 순회하는 것은 트리를 순서대로 순회해야하므로 선형 시간 복잡도 O(N)를 가진다.
