# (Effective Kotlin Item 53) Kotlin - 더 이상 사용하지 않는 객체 참조를 삭제하라

#### 더 이상 사용하지 않는 객체 참조를 삭제하라

* 메모리를 자동으로 관리해주는 언어를 사용하는 개발자들은 객체에 할당된 메모리를 해제하는 것에 별로 신경을 쓰지 않는다.
* 예를 들어, 자바에서는 가비지 컬렉터(GC)가 메모리를 정리한다. 하지만 메모리 관리하는 법을 잊어버리게 되면 메모리 누수로 이어지고, 경우에 따라서 `OutOfMemoryError(메모리 부족 오류)`가 발생할 수 있다.
* 가장 중요한 규칙은 '더 이상 사용되지 않는 객체에 대한 참조가 있으면 안 된다'는 것이다. 메모리를 많이 차지하는 객체가 있거나 객체 인스턴스가 대량 생성될 경우 특히 유념해야되는 규칙이다.
* 리소스를 정적으로 저장하지 않는 것이 가장 좋은 방법이다. 리소스를 정적으로 저장하기보다 의존성을 적절하게 관리해야 한다. 그리고 객체 내부에서 다른 객체를 참조하고 있을 경우 메모리 누수가 발생할 수 있다는 점을 명심해야 한다.

```kotlin
// ❌ Bad
class Stack<E> {
    private var elements = arrayOfNulls<Any?>(DEFAULT_CAPACITY)
    private var size = 0

    fun push(e: E) {
        ensureCapacity()
        elements[size++] = e
    }

    @Suppress("UNCHECKED_CAST")
    fun pop(): E {
        if (size == 0) throw EmptyStackException()
        return elements[--size] as E     // ← 여기가 문제
    }

    private fun ensureCapacity() {
        if (elements.size == size) {
            elements = elements.copyOf(2 * size + 1)
        }
    }

    companion object {
        private const val DEFAULT_CAPACITY = 16
    }
}
```
* `pop` 연산에서 문제가 된다. 스택의 크기만 줄이고 배열에 할당도니 요소를 해제하지 않고 있기 때문이다.
* 스택에 1000개의 요소가 있고, 그것들을 하나씩 `pop`해서 스택 사이즈가 1이 될 때까지 거의 다 `pop`을 했다고 가정하자. 스택에서 단 하나의 요소에만 접근할 수 있기 때문에, 저장하고 있는 요소의 개수도 한 개가 되어야 한다. 하지만 스택은 여전히 1000개의 요소를 가지고 있기에 가비지 컬렉터가 제거할 수 없는 상황이 된다.
* 스택에 남아 있는 요소들이 메모리를 낭비하고 있기 때문에 메모리 누수가 발생한다. 메모리 누수가 계속되면 `OutOfMemoryError`가 발생할 수 있다. 더 이상 필요하지 않은 객체를 `null`로 설정하면 된다.

```kotlin
@Suppress("UNCHECKED_CAST")
fun pop(): E {
    if (size == 0) throw EmptyStackException()
    val result = elements[--size] as E
    elements[size] = null      // 다 쓴 참조를 명시적으로 끊는다
    return result
}
```
* 더 이상 필요하지 않은 값들이 무엇인지 확인하고 해제해야 한다는 규칙은 거의 모든 클래스에 적용된다. 또 다른 예로, `mutableLazy` 프로퍼티 위임이 필요하다고 가정하자. `lazy`처럼 동작하지만 프로퍼티 상태를 변경할 수 있는 차이가 있다.
* 이 때, 초기자(initializer) 값을 `null`로 설정하면 이전 값들은 가비지 컬렉터에 의해 회수될 수 있다.

> **❓객체를 해제하는 것이 최적화에 많은 도움이 될까?**
> * 결론부터 말하자면 모른다. 람다 표현식으로 무엇을 캡처하는지에 따라 다르다.
> * 대부분의 경우 최적화에 큰 영향을 주지 않겠지만, 어떤 경우에는 메모리 누수를 초래할 수 있다.
> * 따라서 불필요한 참조가 있다면 `null`로 대체하는 것이 좋다. 할당된 메모리를 가급적 빨리 해제하려면 변수의 스코프를 더 좁은 스코프로 정의하고 캡처하지 않는 것이 좋다.
> * 함수 내의 변수는 함수가 완료된 경우 가비지 컬렉터가 수집한다. 
> * 프로퍼티에 할당된 값은 가비지 컬렉터가 인스턴스를 회수할 때 같이 회수된다. 최상위 또는 `object` 프로퍼티가 무거운 객체를 참조하면 안 된다. 가비지 컬렉터는 여기서 참조한 객체들에 할당된 메모리를 회수할 수 없기 때문이다.
> * 또한 뷰를 약하게 참조하는 것이 좋다. 약하게 참조된 객체는 가비지 컬렉터에 의해 회수될 수 있기 때문에 사용하지 않는 것이 확인되면 곧바로 회수가 가능하다. 약한 참조를 하게 되면 더 이상 보여지지 않는 뷰에 대한 참조를 직접 처리하지 않아도 된다.

* 결론적으로 메모리 누수를 예측하기란 어려우며, 애플리케이션 전체에 문제가 발생할 때까지 모르고 있을 확률이 높다.
* 힙 프로파일러(heap profiler)처럼 특수한 도구를 사용하면 메모리 누수 탐지가 가능하다.
* 데이터 누수를 탐지하는 데 도움이 되는 여러 라이브러리도 있다.
