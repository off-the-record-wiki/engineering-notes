# (Effective Kotlin Item 54) Kotlin - 처리 단계가 둘 이상인 대규모 컬렉션의 경우 시퀀스를 선호하라

#### 처리 단계가 둘 이상인 대규모 컬렉션의 경우 시퀀스를 선호하라

* 종종 `Iterable`과 `Sequence` 차이점을 간과한다.

```kotlin
interface Iterable<out T> {
    operator fun iterator() : Iterator<T>
}

interface Sequence<out T> {
    operator fun iterator() : Iterator<T>
}
```

* 사실상 두 인터페이스의 유일한 차이는 이름이라고 말할 수 있다.
* 하지만 `Iterable`과 `Sequence`는 완전히 다른 용도로 사용되고 있다. 두 객체의 처리 방식 또한 완전히 다르다.
* `Sequence` 연산은 지연되므로 `Sequence`의 중간 함수는 연산을 수행하지 않는다. 그 대신, 이전 `Sequence`에 해당 연산이 추가된 새 `Sequence`를 반환한다.
* `Sequence` 모든 연산은 `toList()` 또는 `count()`와 같은 최종 연산에서 실행된다. 반면 `Iterable`을 처리할 때는 모든 단계에서 `List`와 같은 컬렉션을 반환한다.
* 결론적으로 컬렉션 처리 연산은 컬렉션이 실제로 필요할 때 실행된다고 할 수 있다.
* Kotlin에서 `Sequence`가 지연된다는 점에는 몇 가지 중요한 이점이 있다.
  * 자연스러운 작업 순서를 유지한다.
  * 최소한의 작업만 수행한다.
  * 무한할 수 있다.
  * 모든 단계에서 컬렉션을 만들 필요가 없다.

#### 순서가 중요하다

* `Iterable`과 `Sequence`는 처리되는 방식이 다르기에 작업 순서 또한 다르다.
* `Sequence` 처리는 첫 번째 요소를 가져와 모든 작업을 적용한 후 다음 요소를 가져오는 식으로 진행된다. 이것을 요소별(element-by-element) 순서 또는 지연 처리 순서(lazy order)라고 부른다.
* `Iterable` 처리에서는 첫 번째 작업을 수행하여 전체 컬렉션에 적용한 후 다음 작업으로 이동한다. 이것을 단계별(step-by-step) 순서 또는 즉시 처리 순서(eager order)라고 부른다.
* 따라서 `Sequence` 처리에 사용되는 요소별 순서가 더 자연스럽다. 또한 `Sequence` 처리는 반복문 및 조건문 구조에 맞게 최적화가 가능하므로 저수준의 컴파일러에서 최적화할 수 있는 여지가 많다.

#### 시퀀스는 최소한의 작업만 수행한다

* 결과를 생성하기 위해 모든 단계에서 전체 컬렉션을 처리할 필요가 없는 경우가 많다.
* 수백만 개의 요소가 포함된 컬렉션이 있는데 처리가 끝난 뒤 처음 10개만 가져오는 상황을 가정하자. `Iterable` 처리에는 중간 연산이라는 개념이 없으므로 모든 작업에서 처리 완료된 컬렉션이 반환된다. `Sequence`는 그럴 필요가 없으므로 최소한의 작업만 수행하여 결과를 도출한다.
* 따라서 몇 가지 중간 연산이 있고 최종 연산을 모든 요소에 대해 수행할 필요가 없다면 `Sequence`를 사용하는 것이 성능상 유리할 가능성이 높으며 실제로도 그렇다.

#### 시퀀스는 무한할 수 있다

* 시퀀스는 필요할 때마다 요소 하나씩 처리되기 때문에 무한 시퀀스를 가질 수 있다.
* 무한 시퀀스를 생성하는 일반적인 방법은 `generateSequence` 또는 `sequence`와 같은 시퀀스 제너레이터를 사용하는 것이다.
* `generateSequence` 매개변수는 시퀀스 첫 번째 요소, 그리고 다음 요소가 무엇인지 계산하는 함수 2가지이다.

```kotlin
generateSequence(1) { it + 1 }
    .map { it * 2 }
    .take(10)
    .forEach { print("$it, ") }
```
* `sequence`는 요청 시 다음 숫자를 생성하는 중단 함수(suspending function)를 사용한다.
* 다음 숫자를 요청할 때마다 시퀀스 빌더를 `yield`를 사용하여 값이 산출될 때까지 실행된다.
* 실행이 끝나면 다음 요청이 올 때까지 실행이 중지된다.
* 무한 시퀀스를 사용할 때는 반드시 생성할 요소의 수를 정해야 한다. 무한 반복하는 것은 불가능한 일이기 때문이다.
* 따라서 `take`와 같은 연산을 사용하여 생성할 요소 수를 제한하거나 `first`, `find` 또는 `indexOf`와 같은 모든 요소가 필요하지 않은 최종 연산을 사용해야 한다.
* 이런 최종 연산들은 모든 요소를 처리할 필요가 없기 때문에 시퀀스에서 사용하는 것이 더 효율적이다.

#### 시퀀스는 모든 처리 단계에서 컬렉션을 생성하지 않는다

* 표준 컬렉션 처리 함수는 모든 단계에서 새 컬렉션을 반환한다. 대부분 `List`이다.
* 모든 단계에서 컬렉션을 생성하기 때문에 언제든지 사용할 수 있다는 장점이 있지만, 비용이 커질수도 있다.
* 중간 연산의 컬렉션 또한 새로 생성해야 하며 결과 데이터를 채워야 한다.

```kotlin
// ❌ Bad
numbers
    .filter { it % 10 == 0 }    // 여기서 1개의 컬렉션
    .map { it * 2 }             // 여기서 1개의 컬렉션
    .sum()                      // 내부적으로 총 2개의 컬렉션이 생성된다.
```

* 요소 개수가 많은 컬렉션 또는 무거운 객체를 가지고 있는 컬렉션에서 문제가 발생할 가능성이 높다.
* 모든 처리 단계에서 컬렉션의 모든 데이터를 할당하는 것은 엄청난 메모리 낭비가 될 수 있다.
* 따라서 파일이나 무거운 객체를 처리할 때는 기본적으로 시퀀스 사용을 권장한다.

#### 시퀀스가 더 빠르지 않을 때는 언제인지?

* 전체 컬렉션의 모든 요소에 대해 연산해야 한다면 시퀀스를 사용해도 효과가 없다.
* `Sequence`에 `sorted`와 같은 메서드가 있다는 사실이 논란의 여지가 된다. 시퀀스의 `sorted` 메서드는 다음 요소를 계산하기 위해 모든 요소가 필요합니다.
* 따라서 첫 번째 요소를 가져올 때만 지연 연산이 수행되며, 이 때 모든 요소를 가져와야 하므로 무한 시퀀스로 만드는 것은 불가능하다.

#### 자바 스트림은 어떤가?

* 자바 8에서는 컬렉션 처리를 허용하는 스트림을 도입했다. 자바 스트림은 코틀린 시퀀스와 형태와 동작 모두 비슷하다.
* 자바 8 스트림은 지연 스트림이며, 마지막 처리 단계에서 연산을 수행한다. 자바 스트림과 코틀린 시퀀스의 3가지 큰 차이점은 다음과 같다.
* 코틀린 시퀀스에는 더 많은 처리 기능이 있으며 일반적으로 사용하기 쉽다. 자바에서는 `collect(Collectors.toList())`를 사용하지만 코틀린에서는 `toList()`로 간단하게 사용할 수 있다.
* 병렬 함수를 사용하면 자바 스트림 처리를 병렬로 처리할 수 있다. 다중 코어가 있는 시스템에서 성능을 크게 향상시킬 수 있다. 하지만 자바 스트림 병렬 처리에 위험 요소가 있으므로 조심해서 사용해야 한다.
* 코틀린 시퀀스는 일반 모듈, 코틀린/JVM, 코틀린/JS, 코틀린/Native 모듈에서 사용할 수 있다. 자바 스트림은 코틀린/JVM에서만 사용할 수 있으며 JVM 버전이 8 이상인 경우에만 사용할 수 있다.

#### 결론

* 컬렉션 처리 비용의 상당 부분은 새로운 컬렉션을 생성하는 데 든다.
* `map`을 사용할 때와 같이 새 컬렉션의 크기를 미리 알면 이 비용이 더 작아지고, `filter`를 사용할 때처럼 새 컬렉션의 크기를 미리 알지 못하면 비용은 커진다.
* 코틀린은 `ArrayList`를 기본 `List`로 사용하는데 내부에서 사용하는 배열의 크기가 요소의 수보다 작으면 배열을 복사하게 되므로 생성할 리스트 크기를 아는 것이 중요하다.
* 시퀀스 처리는 `toList`, `toSet` 등으로 끝나는 경우에만 컬렉션을 생성한다. 그러나 시퀀스의 `toList`는 새 컬렉션의 크기를 미리 알 수 없다.
* 컬렉션을 생성하고 데이터로 채우는 것은 컬렉션 처리 비용의 상당 부분을 차지한다. 따라서 대규모 컬렉션을 처리할 때 중간 연산이 2개 이상이라면 시퀀스를 사용하는 것이 낫다.
* 대규모 컬렉션이란 요소의 개수가 많은 컬렉션 그리고 요소의 크기가 커서 무거운 컬렉션 모두를 말한다.
* 수만 개의 요소가 포함된 정수 목록일 수도 있고 길이가 너무 길어 용량이 MB 단위인 문자열 몇 개만 포함된 목록일 수도 있다. 이런 상황은 일반적인 상황은 아니지만 가끔 발생한다.
