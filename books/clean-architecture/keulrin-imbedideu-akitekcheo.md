# (Clean Architecture 29) - 클린 임베디드 아키텍처

#### 인터페이스를 통하고 대체 가능성을 높이는 방향으로 프로그래밍하라

* 인터페이스에 의존 : "어떻게 하는지"(구현)가 아니라 "무엇을 하는지"(인터페이스)만 알게 한다.
* 인터페이스는 쓰는 쪽이 소유 : 인터페이스를 업무 규칙(높은 수준) 쪽에 두어야 의존이 안쪽을 향한다.
* 진짜 대체 가능 : 어떤 구현을 넣어도 약속한 동작이 같아야 한다. 시그니처만 맞추는 것으로는 부족하다.
* 경계에만 적용 : DB, 외부 API, 프레임워크처럼 자주 바뀌는 것과 업무 규칙 사이에만 쓴다. 모든 클래스에 붙이면 비용만 는다.
* 얻는 것 : 구현을 교체할 수 있고, 테스트할 때 가짜 구현을 끼울 수 있고, DB나 프레임워크 같은 결정을 미룰 수 있다.

#### DRY 원칙: 조건부 커파일 지시자를 반복하지 말라

* DRY(Don’t Repeat Yourself)는 같은 지식(규칙, 결정)을 시스템 안에서 한곳에만 두라는 원칙이다.

1. 환경별 분기 → 조립 시점에 한 번만

* 서비스 곳곳에 `if ("prod".equals(env))`를 쓰는 것을 지양한다.
* 인터페이스 하나에 구현을 여러 개 두고 `@Profile("prod")`나 `@ConditionalOnProperty`로 어떤 Bean을 쓸지 한 번만 고르게 한다.

2. 타입별 분기 → 전략 Bean으로

* `switch (payType)`가 여러 서비스에 반복된다.
* `PaymentStrategy` 구현체마다 Bean으로 등록하고 `Map<String, PaymentStrategy>`로 주입받아 골라 쓴다. 새로운 타입이 생겨도 클래스 하나만 추가하면 된다.

3. 공통 관심사 → 프레임워크 기능으로

* 로깅, 트랜잭션, 권한 체크는 AOP나 `@Transactional`로 처리한다.
* 예외 처리는 `@RestControllerAdvice` 한 곳에서 한다.
* 입력 검증은 Bean Validation을 사용한다.

4. 설정값과 상수 → 한곳에 묶기

* 매직 넘버나 URL을 흩어 두지 말고 `@ConfigurationProperties`로 묶는다.
* 상태와 그 상태에 딸린 동작은 동작을 가진 enum으로 모은다.

5. 업무 규칙 → 엔티티나 도메인 안에

* "할인 계산", "주문 가능 여부"같은 규칙을 Controller, Service, Batch 등에 복사하지 말고 `Order.calculateTotal()`처럼 도메인 한 곳에 둔다.
