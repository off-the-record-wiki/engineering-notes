# (Clean Architecture 18) - 경계 해부학

#### 두려운 단일체

![](https://github.com/user-attachments/assets/f9ac695f-0af3-4a4a-93f3-d72da275a23f)

* 단일체는 시스템 전체가 하나의 실행 파일로 빌드되고, 하나의 프로세스로 실행되는 구조다. 크기와는 무관하다.
* "두려운"은 모놀리스를 무조건 나쁘게 보는 시선을 비꼰 반어적 표현이다.

1. 특징

* 소스는 여러 패키지나 모듈로 나뉘어 있어도 배포는 항상 통째로 한다.
* 모든 코드가 같은 메모리 공간에서 돈다.
* 컴포넌트끼리의 통신은 전부 함수 호출이다.
* 결합 분리 모드 중 소스 수준 분리에 해당한다. 경계가 물리적으로 드러나지 않는다.

2. 그래도 경계는 존재할 수 있다.

* 물리적으로 나뉘지 않았다고 해서 경계가 없는 것은 아니다.
* 다형성(인터페이스)으로 경계를 긋는다. 고수준(업무 규칙)이 인터페이스를 소유하고, 저수준(세부 사항)이 인터페이스를 구현한다.
* 그러면 실행 흐름은 고수준에서 저수준으로 흐르지만 소스 의존은 저수준에서 고수준으로 즉, 반대 방향으로 향한다.
* 뒤집힌 의존 덕분에 고수준 코드는 저수준의 변경으로부터 보호된다.

3. 장점

* 경계를 넘는 비용이 가장 싸다. 함수 호출 한 번이면 되고, 직렬화나 네트워크 지연, 부분 장애 같은 걱정이 없다.
* 단순하다. 빌드, 배포, 운영, 디버깅, 트랜잭션 처리가 모두 쉽다.
* 경계를 잘 지켰다면 여러 팀이 서로의 소스를 건드리지 않고 독립적으로 개발할 수 있다.

4. 한계

* 독립적인 배포가 안 된다. 일부만 바뀌어도 전체를 다시 빌드하고 배포해야 한다.
* 독립적인 실행도 안 된다. 장애나 확장을 컴포넌트별로 나눠 처리할 수 없다.
* 경계가 물리적으로 강제되지 않아서 규율이 무너지면 의존이 아무 방향으로나 얽히기 쉽다. 단일체가 실제로 두려워지는 이유가 바로 이것 때문이다.

#### 배포형 컴포넌트

![](https://github.com/user-attachments/assets/0fefef90-2a9e-47c5-85a6-8eba26c9d3dd)

1. 특징

* 컴포넌트마다 별도의 파일로 빌드되고, 따로 버전이 관리된다.
* 실행할 때는 이 파일들을 한 프로세스에 함께 올려서 돌린다. 동적 링크나 클래스패스 같은 방식이다.
* 그래서 실행 측면에서는 단일체와 같다. 같은 메모리 공간을 쓰고, 통신도 함수(메서드) 호출이다.

2. 경계를 긋는 방식

* 단일체와 똑같이 다형성(인터페이스)으로 긋는다.
* 고수준 컴포넌트가 인터페이스를 소유하고 저수준 컴포넌트가 그걸 구현한다.
* 의존 화살표는 저수준 배포 단위에서 고수준 배포 단위로 향한다.

3. 단일체 대비 얻는 것

* 부분 교체 : 바뀐 컴포넌트의 파일만 새로 빌드해서 바꿔 끼우면 된다. 인터페이스가 그대로라면 나머지는 다시 컴파일하거나 빌드할 필요가 없다.
* 독립 버전 관리 : 컴포넌트별로 릴리스 번호를 붙이고, 사용하는 쪽에서 업그레이드 시점을 정할 수 있다.
* 팀 독립성 강화 : 경계가 파일 단위로 물리적으로 드러나서 단일체보다 경계를 무너뜨리기 어렵다.

4. 그대로인 것(한계)

* 경계를 넘는 비용은 여전히 함수 호출 수준이라 싸다. 이건 장점이기도 하다.
* 하지만 독립 실행은 안 된다. 한 프로세스라서 한 컴포넌트의 장애가 전체를 멈출 수 있고 컴포넌트별로 따로 확장할 수도 없다.
* 배포 단위가 늘어나는 만큼 버전 호환성 관리가 생긴다. 의존성 그래프에 순환이 있으면 독립 배포 이점이 사라진다.
