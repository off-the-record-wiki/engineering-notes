# (Clean Architecture 7) - SRP: 단일 책임 원칙

#### SRP: 단일 책임 원칙

* 함수는 반드시 하나의, 단 하나의 일만 해야 한다는 원칙이다. 이 원칙은 커다란 함수를 작은 함수들로 리팩터링하는 저수준에서 사용된다.

1. 징후 - 우발적 중복

![](https://github.com/user-attachments/assets/d4879979-1889-468d-9c9f-8177dc40d841)

* 문제: 바뀌는 이유가 다른 코드(회계팀용 · 인사팀용)를 같아 보인다고 하나로 합치면 한쪽을 고칠 때 다른 쪽이 몰래 깨진다.
* 해결: 액터별로 클래스를 나눈다. 쓰기 불편하다면 퍼싸드로 묶는다.
* 기준: 모양이 같은지가 아니라 "누가 바꾸는가"로 판단한다. 바꾸는 사람이 다르면 중복이 아니다.

2. 징후 - 병합

![](https://github.com/user-attachments/assets/74817493-5a5e-4c2a-bae2-354996cb1d05)

* 상황: DBA팀 개발자는 CTO 요청으로 `save()`를 고치고 인사팀 개발자는 COO 요청으로 `reportHours()`를 고친다. 둘 다 같은 `Employee.java` 파일을 수정한다.
* 병합 충돌: 두 브랜치를 합칠 때 필드, `import`, 공통 메서드처럼 겹치는 부분에서 충돌이 발생한다.
* 위험: 충돌을 해결하는 사람은 두 팀이 업무를 모두 이해해야 하므로 실수로 한쪽 기능을 깨뜨리기 쉽다.

#### 정리

* 단일 책임 원칙은 메서드와 클래스 수준의 원칙이다.
* 하지만 이보다 상위의 두 수준에서도 다른 형태로 다시 등장한다.
* 컴포넌트 수준에서는 공통 폐쇄 원칙이 된다. 아키텍처 수준에서는 아키텍처 경계의 생성을 책임지는 변경의 축이 된다.
