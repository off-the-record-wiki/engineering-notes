# (Clean Architecture 14) - 컴포넌트 결합

#### ADP: 의존성 비순환 원칙

![](https://github.com/user-attachments/assets/84bddb91-31b4-46a5-8455-2acf0290aa91)

* ADP가 막는건 자신이 아무것도 건드리지 않았는데 타인의 변경 때문에 자신의 코드가 깨지는 상황을 막는다.
* 여럿이 같은 코드를 고치다 보면 어제 잘 돌 던 코드가 아침에 깨지는 문제가 발생한다.
* 팀마다 자기 `jar`를 맡고, 다른 팀 `jar`는 릴리스된 버전에만 의존한다.

1. 주 단위 빌드(Weekly Build)

* 주 단위 빌드는 중간 규모 프로젝트에서 흔하게 사용된다.
* 월~목: 개발자마다 자기 코드 사본으로 작업하고 남이 뭘 바꾸든 자신은 영향을 받지 않는다.
* 금: 모두의 변경을 한꺼번에 합쳐 빌드하고 통합한다.
* 문제점: 금요일에 통합 지옥이 온다. 일주일 치 변경을 한 번에 합치기 충돌과 버그가 몰려서 터진다. 통합시간이 점점 늘어나고 악순환에 빠져 피드백이 느리다.

2. 순환 의존성 제거하기

* 개발 환경을 릴리스 가능한 컴포넌트 단위로 분리하는 것이다.
* 개발자가 해당 컴포넌트가 동작하도록 만든 후 해당 컴포넌트를 릴리스하여 다른 개발자가 사용할 수 있도록 만든다.
* 담당 개발자는 이 컴포넌트에 릴리스 번호를 부여하고 다른 팀에서 사용할 수 있는 디렉터리로 이동시킨다.

![](https://github.com/user-attachments/assets/839f0c9c-3d33-4fb4-9aba-d2a6a3b2d944)

#### 순환이 컴포넌트 의존성 그래프에 미치는 영향

![](https://github.com/user-attachments/assets/b345a888-508b-42ed-b746-0ba763cc0f33)

* 원인: Entities의 User가 Authorizer의 Permissions를 쓰면서 Entities → Authorizer → Interactors → Entities로 도는 순환이 발생한다.
* 결과: 3개의 컴포넌트는 사실상 하나로 묶어서 하나만 바꿔도 3개를 빌드하고 릴리스해야 한다.
