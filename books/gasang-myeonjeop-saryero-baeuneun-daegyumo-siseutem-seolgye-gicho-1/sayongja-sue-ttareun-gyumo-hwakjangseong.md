# 가상 면접 사례로 배우는 대규모 시스템 설계 기초 1 - 사용자 수에 따른 규모 확장성

#### 데이터베이스

![](https://raw.githubusercontent.com/wiki/thought-corner/study/images/attachments/badca0b7-266a-4bb5-8e6d-a91e0b5b8b52.png)

* 사용자가 늘어나면 서버 하나로는 충분하지 않아서 여러 서버를 두게 된다.
* 하나는 웹/모바일 트래픽 처리 서버(웹 계층)와 데이터베이스 서버(데이터 계층)를 분리하면 그 각각을 독립적으로 확장해 나갈 수 있게 된다.

#### 어떤 데이터베이스를 사용할 것인가?

**1. 관계형 데이터베이스(RDB)**

* 관계형 데이터베이스는 데이터를 테이블 형태로 저장한다.
* 행(row)과 열(column)로 이루어지며, 행은 레코드 하나, 열은 속성 하나에 해당한다.
* 흔히 이를 관리하는 소프트웨어를 포함해 RDBMS라고 부르며, MySQL, PostgreSQL, Oracle 등이 대표적이다.
* 가장 큰 특징은 SQL을 사용한다는 점이다. 테이블끼리 키(기본 키, 외래 키)로 관계를 맺어 두고, 필요할 때 JOIN으로 여러 테이블의 데이터를 합쳐 조회할 수 있다.

**2. 비관계형 데이터베이스(NoSQL)**

* NoSQL은 테이블 간 관계를 전제로 하지 않는 데이터베이스를 통칭하는데 저장 방식에 따라 4가지로 나뉜다.
  * 키-값 저장소 : 키 하나에 값 하나를 저장하는 단순한 구조(예: Redis, DynamoDB)
  * 문서 저장소 : JSON 같은 문서 단위로 저장(예: MongoDB, CouchDB)
  * 칼럼 저장소 : 열 단위로 데이터를 묶어 대량 데이터를 분산 저장(예: Cassandra, HBase)
  * 그래프 저장소 : 노드와 간선으로 관계 자체를 저장(예: Neo4j)
* 일반적으로 조인 연산을 지원하지 않기 때문에, 함께 조회할 데이터는 처음부터 한 곳에 묶어 저장하는 방식으로 설계한다.
* 스키마가 유연하고 수평 확장이 쉽다는 장점이 있다.

> **비관계형 DB가 바람직한 경우**
* 아주 낮은 응답 지연시간(latency)이 필요할 때
* 다루는 데이터가 비정형이라 관계형 구조로 표현하기 어려울 때
* 데이터를 직렬화/역직렬화(JSON, XML, YAML 등)해서 저장만 하면 될 때
* 아주 많은 양의 데이터를 저장해야 할 때

#### 수직적 규모 확장 vs 수평적 규모 확장

**1. 수직적 규모 확장(스케일 업, Scale Up)**

* 기존 서버 한 대의 사양을 높이는 방식이다. 더 좋은 CPU로 바꾸거나 RAM, 디스크를 늘려서 그 서버가 더 많은 일을 처리하게 만든다.
* 가장 큰 장점은 단순함이다. 서버가 여전히 한 대이기 때문에 애플리케이션 구조를 바꿀 필요가 없고, 트래픽이 많지 않은 초기 단계에서는 좋은 선택이다.
* 하지만 확장에 한계가 있다. 한 대의 서버에 꽂을 수 있는 CPU와 메모리에는 물리적 상한이 있고, 사양으로 갈수록 비용도 급격히 올라간다.
* 장애 대응이 불가능하다. 서버가 한 대뿐이라 자동복구(failover)나 다중화(redundancy) 방안이 없다. 그 서버가 죽으면 웹/앱 서비스 전체가 멈춘다. 이런 지점을 단일 장애 지점(SPOF, Single Point of Failure)이라고 부른다.

**2. 수평적 규모 확장(스케일 아웃, Scale Out)**

* 서버의 대수를 늘리는 방식이다. 비슷한 사양의 서버를 여러 대 두고 요청을 나눠서 처리한다.
* 확장 한계가 사실상 없다. 트래픽이 늘면 그에 따라 서버를 더 추가하면 된다.
* 장애에 강하다. 서버 한 대가 고장 나도 나머지 서버가 요청을 이어받아 서비스가 계속 유지된다.

#### 로드밸런서(Load Balancer)

![](https://raw.githubusercontent.com/wiki/thought-corner/study/images/attachments/9b63e5bf-852c-4e3e-a29e-56fe2ec2f93f.png)

* 로드밸런서는 여러 대의 웹 서버 앞에 서서, 들어오는 요청을 서버들에게 골고루 나눠 주는 장치이다.
* 이 때 로드밸런서가 요청을 나눠 줄 대상 서버들의 묶음을 부하 분산 집합(Load Balancing Set)이라고 한다.
  * 사용자는 로드밸런서의 공개 IP로만 접속한다.
  * 웹 서버는 사용자의 요청을 직접 받지 않는다. 로드밸런서와 웹 서버는 사설 IP로 통신하는데, 사설 IP는 같은 네트워크 안에서만 접근 가능해서 외부에서 서버로 직접 들어올 수 없으므로 보안에도 유리하다.
* 장애 대응(failover) : 서버 A가 다운되면 로드밸런서가 모든 트래픽을 서버 B로 보낸다. 서버 한 대가 죽어도 웹 사이트 전체가 멈추지 않으니 스케일 업에서 문제였던 단일 장애 지점(SPOF)이 사라진다. 필요하면 새로운 서버를 추가해 다시 부하를 나눌 수 있다.
* 트래픽 급증 대응 : 트래픽이 가파르게 늘어서 2대도 감당이 안 되는 시점이 오더라도, 웹 서버 계층에 서버를 추가하기만 하면 된다. 로드밸런서가 새로운 서버에도 자동으로 트래픽을 분산하기 시작하므로 서비스 구조를 바꾸지 않고 대처가 가능하다.

#### 데이터베이스 다중화

![](https://raw.githubusercontent.com/wiki/thought-corner/study/images/attachments/11d7dd75-cc88-448c-810c-507d363cb364.png)

* 데이터베이스 다중화는 DB 서버를 여러 대 두고 역할을 나누는 방식이다. 보통 주(Master) - 부(Slave) 관계로 구성한다.
  * 주 DB : 쓰기 연산만 담당. 데이터를 바꾸는 INSERT, UPDATE, DELETE 같은 명령은 반드시 주 DB로만 보낸다.
  * 부 DB : 주 DB로부터 데이터 사본을 전달받고 읽기 연산만 담당한다.
* 부 DB가 더 많은 이유는 대부분의 서비스는 읽기가 쓰기보다 훨씬 많기 때문이다.
* 성능 : 쓰기는 주 DB 한 곳으로, 읽기는 여러 부 DB로 분산되니 동시에 처리할 수 있는 질의 수가 늘어난다.
* 안정성 : 데이터를 지역적으로 떨어진 여러 곳에 복제해 둘 수 있어 재해로 일부 서버가 파괴되어도 데이터가 보존된다.
* 가용성 : DB 서버 하나에 장애가 나도 다른 서버의 데이터로 서비스를 계속 이어갈 수 있다.

> **장애가 발생하면 어떻게 되는지**
* 부 DB가 다운된 경우 : 다른 부 DB가 있다면 읽기를 그쪽으로 넘기고 부 DB가 하나뿐이었다면 잠시 주 DB가 읽기까지 처리한다. 이후 새로운 부 DB로 교체한다.
* 주 DB가 다운된 경우 : 부 DB 하나를 새로운 주 DB로 승격시킨다. 다만 부 DB 데이터가 최신이 아닐 수 있기에 복구 스크립트로 빠진 데이터를 채워야 하는 경우가 필요하다. 실제 운영에서는 이 과정이 꽤 까다롭다.

#### 최종 설계안

![](https://raw.githubusercontent.com/wiki/thought-corner/study/images/attachments/a9a05731-e6d9-4273-b636-17ea36cd5f86.png)

1. 사용자는 DNS로부터 로드밸런서의 공개 IP 주소를 받는다.
2. 사용자는 해당 IP 주소를 사용해 로드밸런서에 접속한다.
3. HTTP 요청은 웹 계층의 여러 서버 중 하나에 전달된다.
4. 웹 서버는 사용자의 데이터를 부 데이터베이스 서버에서 읽는다.
5. 웹 서버는 데이터 변경 연산은 주 데이터베이스로 전달한다. 데이터 추가, 삭제, 갱신 연산 등이 이에 해당한다.

#### 캐시(Cache)

* 캐시는 값비싼 연산 결과나 자주 참조되는 데이터를 메모리에 저장해 두고 다음 요청이 왔을 때 빠르게 돌려주는 저장소이다.
* 디스크 기반인 데이터베이스보다 메모리가 훨씬 빠르기 때문에 응답 속도가 크게 좋아진다.
* 웹 페이지를 새로고침할 때마다 화면에 보여 줄 데이터를 가져오느라 데이터베이스 호출이 한 번 이상 일어난다.
* 사용자가 많아지면 이 호출이 쌓여 DB에 부하가 몰리고 결국 애플리케이션 성능은 DB를 얼마나 자주 호출하느냐에 크게 좌우된다.

#### 캐시 계층(Cache Tier)

* 캐시 계층은 웹 서버와 데이터베이스 사이에 두는 임시 데이터 보관소이다. 메모리 기반이라 데이터베이스보다 훨씬 빠르다.
* 성능 개선 : 자주 쓰는 데이터를 빠른 메모리에서 바로 꺼내 준다.
* DB 부하 감소 : 캐시가 대신 응답하는 만큼 DB로 가는 질의가 줄어든다.
* 독립적인 확장 : 캐시 계층이 DB와 분리되어 있어서, 캐시 서버만 따로 늘리거나 줄일 수 있다. 웹 계층, 데이터 계층처럼 캐시도 하나의 독립된 계층으로 다루는 셈이다.

> **요청 처리 흐름**
* 요청을 받은 웹 서버가 먼저 캐시에 응답이 있는지 확인한다.
* 있으면(캐시 히트) → 그 데이터를 바로 클라이언트에 반환한다.
* 없으면(캐시 미스) → DB에 질의해 데이터를 찾고, 캐시에 저장한 뒤 클라이언트에 반환한다.

#### 캐시 사용 시 유의할 점

> **1. 캐시는 어떤 상황에서 사용하는 것이 좋을까?**
* 데이터 변경은 드물고 조회가 매우 빈번한 경우, 동일한 요청이 반복적으로 발생하는 경우, 응답 속도가 중요한 API인 경우가 적합
* 실시간 정확성이 중요한 데이터(재고 수량, 계좌 잔액 등)는 캐시와 원본이 어긋날 위험이 있어 신중하게 써야 한다.

> **2. 어떤 데이터를 캐시에 두어야 하는가?**
* 캐시는 데이터를 휘발성 메모리에 두므로 영속적으로 보관할 데이터를 캐시에 두는 것을 바람직하지 않다.
* 중요 데이터는 여전히 지속적 저장소(persistent data store)에 두어야 한다.
* 조회가 잦은 데이터, 계산 비용이 큰 결과(집계, 랭킹), 세션 정보, 설정값 등은 두면 좋다.

> **3. 캐시에 보관된 데이터는 어떻게 만료되는가?**
* 만료된 데이터는 캐시에서 삭제되어야 한다.
* 만료 정책이 없으면 데이터는 계속 캐시에 남게 된다.
* 만료 기한은 너무 짧으면 곤란한데, 데이터베이스를 너무 자주 읽게 될 것이기 때문이다.
* 반대로 너무 길어도 곤란한데, 원본과 차이가 날 가능성이 높아지기 때문이다.
* 많은 키의 만료 시간이 동시에 끝나면 DB로 요청이 한꺼번에 몰리는 문제(캐시 스탬피드)가 생길 수 있어서, TTL에 약간의 랜덤 값을 더해 만료 시점을 흩어 놓기도 한다.

> **4. 일관성(consistency)은 어떻게 유지되는가?**
* 일관성은 데이터 저장소의 원본과 캐시 내의 사본이 같은지 여부이다.
* 저장소의 원본을 갱신하는 연산과 캐시를 갱신하는 연산이 단일 트랜잭션으로 처리되지 않은 경우 이 일관성은 깨질 수 있다.
* DB를 갱신할 때 해당 캐시 키를 삭제해서 다음 조회 때 새로 채우게 하는 방식이 가장 흔하다.
* DB와 캐시를 동시에 갱신하는 쓰기 관통(write-through) 방식도 있다. 대부분은 완벽한 일관성 대신 짧은 불일치를 허용하는 선에서 타협한다.

> **5. 장애에는 어떻게 대처할 것인가?**
* 캐시 서버를 한 대만 두는 경우 해당 서버는 단일 장애 지점(SPOF, Single Point of Failure)이 되어버릴 가능성이 있다.
* 결과적으로 SPOF를 피하려면 여러 지역에 걸쳐 캐시 서버를 분산시켜야 한다.
* 캐시 서버를 여러 대(여러 지역)에 분산하면 한 대가 죽어도 다른 서버가 응답하고, 최악의 경우에도 DB에서 데이터를 가져오면 되므로 서비스가 멈추지 않는다.

> **6. 캐시 메모리는 얼마나 크게 잡을 것인가?**
* 캐시 메모리가 너무 작으면 액세스 패턴에 따라서 데이터가 너무 자주 캐시에서 밀려나버려 캐시 성능이 저하된다.
* 이를 막을 한 가지 방법은 캐시 메모리를 과할당하는 것이다.
* 이렇게 하면 캐시에 보관될 데이터가 갑자기 늘어났을 때 생길 문제도 방지할 수 있다.

> **7. 데이터 방출(eviction) 정책은 무엇인가?**
* 캐시가 꽉 차버리면 추가로 캐시에 데이터를 넣어야 할 경우 기존 데이터를 내보내야 한다.
* 이것을 캐시 데이터 방출 정책이라 하는데, 그 가운데 가장 널리 쓰이는 것이 바로 LRU(Least Recently Used)로 마지막으로 사용된 시점이 가장 오래된 데이터를 내보내는 것이다.
* 다른 정책으로는 LFU(Least Frequently Used)로 사용된 빈도가 가장 낮은 데이터를 내보내는 정책, FIFO(First In First Out)로 가장 먼저 캐시에 들어온 데이터를 가장 먼저 내보내는 정책이 있으며 경우에 맞게 적용 가능하다.

#### 컨텐츠 전송 네트워크(CDN)

![](https://raw.githubusercontent.com/wiki/thought-corner/study/images/attachments/ec50de7b-d7b5-4321-ac5f-2bf32f2626b2.png)

* CDN(Content Delivery Network)은 정적 콘텐츠를 빠르게 전달하기 위해 전 세계 여러 지역에 분산 배치된 서버 네트워크이다.
* 이미지, 비디오, CSS, JavaScript 파일처럼 누가 요청해도 내용이 같은 파일을 캐시해둔다.
* 핵심 아이디어는 거리이다. 서울 사용자가 미국에 있는 원본 서버까지 가지 않고 가까운 서울·도쿄의 CDN 서버에서 파일을 받으면 훨씬 빨리 로딩된다. 즉, CDN은 사용자 가까이에 놓인 캐시이다.

> **1. 동작 방식**

1. 사용자 A가 이미지 URL을 이용해 image.png 파일에 접근한다. URL의 도메인은 CDN 서비스 사업자가 제공한다.
2. CDN 서버 캐시에 해당 이미지가 없는 경우, 서버는 원본(Origin) 서버에 요청하여 파일을 가져온다. 원본 서버는 웹 서버일 수도 있고 Amazon S3와 같은 온라인 저장소일 수도 있다.
3. 원본 서버가 파일을 CDN 서버에 반환한다. 응답의 HTTP 헤더에는 해당 파일이 얼마나 오래 캐시될 수 있는지를 설명하는 TTL 값이 들어있다.
4. CDN 서버는 파일을 캐시하고 사용자 A에게 반환한다. 이미지는 TTL에 명시된 시간이 끝날 때까지 캐시된다.
5. 사용자 B가 같은 이미지에 대한 요청을 CDN 서버에 전송한다.
6. 만료되지 않은 이미지에 대한 요청은 캐시를 통해 처리된다.

> **2. 비용**
* CDN은 보통 제 3사업자에 의해 운영되며, 사용자는 CDN으로 들어가고 나가는 데이터 전송 양에 따라 요금을 내게 된다.
* 자주 사용되지 않는 콘텐츠를 캐싱하는 것은 이득이 크지 않으므로, CDN에서 빼는 것을 고려한다.

> **3. 적절한 만료 시한 설정**
* 시의성이 중요한 컨텐츠의 경우 만료 시점을 잘 정해야 한다. 
* 너무 길지도 않고 짧지도 않아야 하는데, 너무 길면 컨텐츠의 신선도는 떨어질 것이고, 너무 짧으면 원본 서버에 빈번히 접속하게 되어서 좋지 않다.
* 파일명에 버전이나 해시를 넣고 TTL은 아주 길게 잡으면 신선도와 원본 부하 문제를 동시에 해결할 수 있다. 파일이 바뀌면 URL 자체가 바뀌기 때문이다.

> **4. CDN 장애에 대한 대처 방안**
* CDN 자체가 죽었을 경우 웹사이트/애플리케이션이 어떻게 동작하는지 고려해야 한다.
* 가령 일시적으로 CDN이 응답하지 않을 경우, 해당 문제를 감지하여 원본 서버로부터 직접 컨텐츠를 가져오도록 클라이언트를 구성하는 것이 필요할 수도 있다.
* 컨텐츠 무효화(Invalidation) 방법 : 아직 만료되지 않은 컨텐츠라 하더라도 아래 방법 가운데 하나를 사용하면 CDN에서 제거할 수 있다
  * API 무효화 : CDN에 있는 기존 파일을 지우는 방식 → 반영까지 시간이 걸릴 수 있다.
  * 버저닝 : 기존 파일은 두고 새 URL로 새 파일을 받게 하는 방식 → 즉시 반영 가능 

#### 무상태(Stateless) 웹 계층

* 상태 정보(사용자 세션 데이터와 같은)를 웹 계층에서 제거해야 한다.
* 바람직한 전략은 상태 정보를 관계형 데이터베이스나 NoSQL 같은 지속성 저장소에 보관하고, 필요할 때 가져오도록 하는 것이다.
* 이렇게 구성된 웹 계층은 무상태 웹 계층이라 부른다.

#### 메시지 큐(Message Queue)

![](https://raw.githubusercontent.com/wiki/thought-corner/study/images/attachments/97860829-5679-46a1-8dab-57e66e6d5c9f.png)

* 메시지 큐는 서비스끼리 비동기로 통신할 수 있게 해 주는 컴포넌트이다. 보내는 쪽이 메시지를 큐에 넣어 두면, 받는 쪽이 준비됐을 때 꺼내 처리한다. 그 사이 큐는 메시지를 잠시 쌓아 두는 버퍼 역할을 한다.
* 생산자(Producer) / 발행자(Publisher) : 메시지를 만들어 큐에 발행하는 서비스
* 메시지 큐 : 메시지를 보관하는 버퍼
* 소비자(Consumer) / 구독자(Subscriber) : 큐에 연결되어 메시지를 꺼내고, 그에 맞는 작업을 수행하는 서비스나 서버

> **왜 쓰나 : 느슨한 결합**
* 메시지 큐의 핵심 장점은 생산자와 소비자를 서로 분리한다는 점이다.
* 서로를 기다리지 않는다 : 생산자는 소비자가 살아 있든 바쁘든 상관없이 메시지만 넣고 다음 일을 한다. 소비자도 생산자가 없어도 쌓인 메시지를 처리할 수 있다.
* 각자 독립적으로 확장할 수 있다. 큐에 메시지가 많이 쌓이면 소비자만 늘리고, 한가해지면 줄이면 된다. 생산자 쪽은 건드릴 필요가 없다.
* 장애에 강하다 : 한쪽이 잠시 멈춰도 메시지가 큐에 남아 있어서 복구 후 이어서 처리할 수 있다.

#### 로그, 메트릭, 자동화

![](https://raw.githubusercontent.com/wiki/thought-corner/study/images/attachments/f532760e-05a4-4e49-80d3-9b208c044755.png)

* 로그 : 에러 로그를 모니터링하면 시스템에서 어떤 오류가 언제, 어디서 났는지 빠르게 찾아낼 수 있다.
* 메트릭 : 메트릭은 시스템과 사업 상태를 숫자로 측정한 값이다. 
* 자동화 : 시스템이 크고 복잡해지면 사람이 손으로 하는 작업은 느리고 실수가 잦아진다. 자동화 도구로 생산성을 높여야 한다.

#### 데이터베이스 규모 확장

![](https://raw.githubusercontent.com/wiki/thought-corner/study/images/attachments/fe7bdcae-219d-4793-8a63-4901728768a5.png)

* 샤딩은 DB 서버를 샤드(Shard)라는 작은 단위로 분할하는 것이다. 모든 샤드는 같은 스키마를 쓰지만, 샤드에 보관되는 데이터 사이에는 중복이 없다.

> **샤딩 전략 구현 시 고려사항**
* 샤딩을 도입할 때 가장 중요한 것은 샤딩 키 (혹은 파티션 키)를 어떻게 정하느냐 하는 것이다. 특히 데이터를 고르게 분할할 수 있도록 적절한 키를 선정하는 것이 중요하다. 다음은 샤딩 도입 시 고려해야 할 것들이다.

> **1. 데이터의 재샤딩**
* 데이터가 너무 많아져서 하나의 샤드로는 더 이상 감당하기 어렵거나, 샤드 간 데이터 분포가 균등하지 못하여 어떤 샤드에 할당된 공간 소모가 다른 샤드에 비해 빨리 진행될 때 필요하다.
* 샤드 키를 계산하는 함수를 변경하고 데이터 재배치 필요하다.

> **2. 유명 인사 문제**
* 핫스팟 키 문제라고도 부르는데, 특정 샤드에 쿼리가 집중되어 서버에 과부하가 걸리는 문제다.

> **3. 조인과 비정규화**
* 일단 하나의 데이터베이스를 여러 샤드 서버로 쪼개고 나면, 여러 샤드에 걸친 데이터를 조인하기가 어렵다.
* DB 비정규화를 고려할 수 있고 하나의 테이블에서 쿼리가 수행될  수 있도록 할 수 있다.
