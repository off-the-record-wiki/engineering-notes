# Claude Code - Advanced Multi-Agent Orchestration: Task Scheduling and BFT-Based Consensus Patterns

#### SubAgent를 어떻게 실제로 적용할 것인지?

* 조사를 생략할 때 생기는 문제 : 조사 없이 바로 구현하면 에이전트가 비교 대상이나 지표를 임의로 정할 수 있다. 먼저 근거를 조사하고 계획에 반영해야 결과물의 이유를 설명하고 수정하기 쉽다.
* 세션 이어가기와 조사 프롬프트 : Setting Source와 Resume을 사용하면 기존 세션의 문맥을 이어서 작업할 수 있다. 조사 결과를 확인한 뒤 계획 승인 화면에서 비교 대상과 지표가 적절한지 검토한다.
* 계획 수립과 구현·검토 자동화 : 계획에 구현 담당과 검토 담당을 지정하고 지침 파일 수정 사항도 포함한다. 이를 바탕으로 계획을 승인하면 구현과 검토가 이어지고 검토에서 발견한 누락 사항은 구현 담당이 다시 수정한다.

#### BFT(비잔티움 문제)를 기반으로 이해하고 사용할 수 있는 병렬 검토 패턴

* 오류 재현과 원인 파악 : 원인이 불분명하거나 영향 범위가 클 수 있는 오류는 바로 수정하지 않고 검사 명령이 실패하는 상태를 재현해 수정 전후를 비교할 기준을 마련한다. 조사 담당 에이전트가 실패 원인을 분석하게 하되 Hook과 Retry가 반복되면 불필요한 토큰을 사용할 수 있다는 점도 유의해야한다.
* 수정 구현과 검토의 반복 : 원인을 파악한 뒤 구현 담당 에이전트가 수정하고 검토 담당 에이전트가 변경 범위와 부작용을 확인한다. 검토에서 문제가 발견되면 수정과 검토를 반복하며 검사 명령이 계속 실패하면 원인 파악 단계로 돌아가야한다.
* 병렬 조사와 합의 결과 검증 : 단일 에이전트의 자기선호편향을 줄이기 위해 서로 다른 관점의 에이전트가 병렬로 조사하고 둘 이상이 공통으로 제시한 항목을 채택한다. 한 곳에서만 나온 항목은 참고 목록으로 분리하고 에이전트들의 의견이 정반대라면 다수결로 결론 내리지 말고 해당 항목을 따로 재조사해야한다.

#### Agent 세션간 통신 구축하기

* 실험 단계 기능과 기존 방식의 차이 : Agent Team은 아직 실험 단계라 실무에 바로 적용하기보다 구조와 가능성을 파악하는 것이 중요하다. 기존 Sub-agent 방식에서는 결과가 메인 세션으로 모이지만 Agent Team에서는 팀원끼리 메시지를 주고받고 공유 작업 목록을 확인할 수 있다.
* 독립 세션의 비용과 기능 활성화 : Sub-agent는 메인 세션 안에서 실행되지만 Agent Team의 팀원은 각자 화면과 기억을 가진 독립 세션이라 비용이 더 높다. 설정 파일에 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`을 추가하고 세션을 다시 연 뒤 팀 구성을 요청하는 프롬프트로 팀원을 실행하도록 한다.
* 공유 작업 목록과 자율적인 분담 : 팀원들은 공유된 할 일 목록에서 작업을 직접 가져가고 새로 발견한 작업도 목록에 올려 다른 팀원이 처리하게 할 수 있다. 메인 세션이 리더 역할을 맡으며 작업 도중 리더가 바뀌지는 않는다.
* Sub-agent와 함께 사용하기 : Agent Team은 기존 멀티 에이전트나 Sub-agent를 대체하는 방식이 아니라 추가 선택지다. 평소에는 Sub-agent를 사용하고 팀원 간 논의가 필요한 상황에만 Agent Team을 구성할 수 있다.
* 실험 기능의 오류와 세션 제약 : 작업 상태가 실제보다 늦게 표시되거나 중단 요청이 즉시 반영되지 않는 등 상태 정보가 부정확할 수 있다. 한 세션에서 팀 하나만 만들 수 있고 중첩 팀도 지원하지 않으며 세션을 나중에 이어서 열 수 없어서 파일 기반 스펙을 활용하는 편이 좋다.
* 통신 필요성에 따른 선택 기준 : 서로 다른 가설을 논의해 합의해야 하거나 여러 작업 영역의 결정이 서로 영향을 주는 경우에는 Agent Team이 유용하다. 순서대로 처리하거나 파일을 수정한 뒤 결과만 받으면 되는 단순 작업에는 더 저렴하고 안정적인 Sub-agent가 적합하다.

#### 정기 작업 예약 실행과 팀 진행 순서 정리

* 정기 작업 예약 방식과 터미널 세션 : 터미널 세션을 켜 둔 채 요청을 반복하는 방식과 macOS 예약 도구를 사용하는 방식을 비교할 수 있다. 세션을 유지하는 방식은 터미널이 열린 상태여야 하고 컴퓨터를 끄거나 슬립 모드로 전환하면 작업이 멈춘다.
* macOS 예약 실행과 `-p` 옵션 : `-p` 옵션으로 대화창을 열지 않고 한 번 요청을 처리한 뒤 종료하도록 예약할 수 있다. 사용자가 로그인해 있어야 실행되며 슬립 중 지나간 예약은 깨어난 뒤 한 번만 실행된다. 24시간 운영이 필요하면 별도의 클라우드를 사용해야한다.
* `claude -p` 단발 실행과 권한 규칙 : 프로젝트 폴더에서 `claude -p` "안녕"을 실행하면 새 세션이 요청에 응답한 뒤 종료된다. 기존 GCHIP 권한 규칙도 적용되므로 예약을 등록하기 전에 명령을 직접 실행해 요청문 오타나 연결 문제를 확인해야한다.
* `LaunchAgent` 예약 목록 확인 : `ls ~/Library/LaunchAgent` 명령으로 현재 등록된 예약 항목을 살펴본다. 다른 프로그램의 항목이 함께 보일 수 있고 폴더가 없거나 출력이 비어 있어도 잘못 입력한 것은 아니다.
* 대화창 없는 예약 작업의 권한과 실행 범위 : 승인 버튼을 눌러 줄 사람이 없으므로 승인에 의존하는 동작은 예약 작업에서 제외해야한다. 허용되지 않은 동작은 기록 파일에 남기고 파일 수정이나 웹 조회처럼 미리 허용한 작업은 승인 없이 수행하도록 지정할 수 있다.
* 예약 등록 확인과 작업 내용 지정 : 예약 등록 후에는 생성된 작업과 설정이 실제로 실행 가능한지 확인한다.
