# Claude Code - Mitigating Self-Preference Bias in AI Using Subagents

#### 테스트 선행 패턴을 통해 결과물 퀄리티 검증

* 테스트 선행 패턴과 하네스 엔지니어링 : 기능을 구현하기 전에 통과 조건과 검증 규격을 먼저 정한다. 자연어로 기준을 전달하면 클로드 코드가 테스트와 기능을 순서대로 구현하도록 하는 방식이다.
* 테스트 실습과 실패 케이스 확인 : 리스크 항목에 위험도 색상을 표시한다.
* 공통 규칙 적용과 테스트 선행의 필요성 : 검증 순서를 `CLAUDE.md`에 공통 규칙으로 추가해 모든 기능 개발에 적용한다. 결과물을 만든 뒤 기준을 정하면 기준이 결과물에 맞춰질 수 있으므로 조건을 먼저 정의하고 실패 여부를 확인한다.
* 비결정적 동작에 대한 재요청 : Claude Code가 지침을 따르지 않아 실패 과정 없이 통과 결과만 보여주는 경우가 생길 수 있다. 넘어가지 말고 구현 전에 테스트가 실패하는 모습을 먼저 보여달라고 요청해 검증 절차를 확인한다.
* 자기선호편향을 줄이는 세션 분리 : 개발과 검토를 같은 세션에서 진행하면 AI 에이전트가 대화 이력에 영향을 받아 자신의 작업물을 제대로 검토하지 못할 수 있다. 기능 개발이 끝난 뒤 새 세션에서 대화 이력 없이 파일만 검토하게 하면 이런 편향을 줄일 수 있다.
* 가독성을 높이는 결과물 규칙 : 읽기 어려운 결과물을 개선하기 위해 `CLAUDE.md`에 대주제·소주제·본문 구조, 카드형 블록, 변수 기반 스타일링, 글자 수 제한 등의 규칙을 추가한다. 지침은 필요에 따라 조정할 수 있으며, 핵심은 하네스나 훅을 활용해 결과물의 규격과 품질을 관리한다.

#### 자기 선호 편향을 해소하기 위한 Subagent 패턴 정의와 테스트

* 단일 세션의 구조적 한계 : 한 세션에서 조사, 구현, 검토를 모두 수행하면 자신이 만든 결과물을 객관적으로 검토하기 어려워진다. 대화 이력에 따른 토큰 비용 증가와 역할마다 다른 작업 특성도 단일 세션의 한계가 있다.
* 서브 에이전트 역할 설계와 도구 제한 : 메인 세션은 오케스트레이터로 두고 조사용 `research`, 구현용 `build`, 검토용 `review`로 역할을 나눈다. `research`와 `review`에는 파일 수정 도구를 제한하고, `build`에만 수정 권한을 부여해 역할을 명확히 한다.
* 컨텍스트 격리와 정의 파일 생성 : 서브 에이전트는 지침 파일과 프로젝트 상태는 활용하지만 메인 세션의 대화 이력과 메모리는 물려받지 않아 자기 선호 편향을 줄일 수 있다.

#### SubAgent는 언제 사용해야하는지?

* 6가지 서브에이전트 역할 정의 : 기획·조사·구현·테스트·검토·기록으로 역할을 나누고, 각 에이전트의 판단 범위와 파일 수정 권한을 구분한다. 특히 테스트는 통과와 실패가 명확한 결과를 확인하고, 검토는 출처 누락이나 요청과 다른 방향처럼 사람의 판단이 필요한 문제를 찾아낸다.
* 작업에 따른 선택적 에이전트 호출 : 에이전트를 6명 모두 만들어두더라도 매번 전부 호출하지 않고 작업의 성격에 맞춰 필요한 역할만 선택한다. 구현은 기본으로 포함하고 애매한 요청에는 기획을 외부 자료가 필요하면 조사를 명확한 통과·실패 조건이나 결과 검토가 필요하면 각각 테스트와 검토를 활용해 토큰 낭비를 줄인다.
* 역할별 모델 등급 지정과 토큰 최적화 : 정해진 절차를 따르는 조사·테스트·기록에는 가벼운 모델을, 실제 계획을 반영하는 구현에는 중간 모델을, 판단이 중요한 기획·검토에는 무거운 모델을 배정한다. 서브에이전트 정의 파일에 `model` 키를 추가하면 역할에 맞는 모델을 지정할 수 있으며 판단이 필요한 역할에 낮은 등급을 쓰면 문제를 놓치고도 검토가 끝난 것처럼 보일 수 있다.
* 서브 에이전트 호출 비용과 트레이드오프 : 작업을 정리해 전달하고 지침과 프로젝트 상태를 읽힌 뒤 결과를 받아오는 과정에는 토큰과 시간이 든다. 작업이 짧고 간단하면 이 준비와 회수 비용이 실제 작업보다 커질 수 있다.
* 작업을 위임할지 판단하는 기준 : 답이 한두 줄로 끝나거나 기존 대화 맥락을 알아야 하는 일은 메인 에이전트가 직접 처리하는 편이 효율적이다. 반대로 크고 독립적이며 기존 맥락에 덜 의존하는 리서치나 객관적 검토는 서브 에이전트에 맡기면 메인 세션의 컨텍스트가 불필요하게 누적되는 것을 줄일 수 있다.
* 워커 수를 늘리는 조건과 점진적 확장 : 작업이 서로 독립적으로 나뉘고, 담당 범위가 겹치지 않으며, 결과를 합치는 비용이 크지 않을 때 워커를 늘리는 것이 유리하다. 처음에는 구현 에이전트 하나로 시작하고 결과가 부족할 때 컴퓨터나 리서치 에이전트를 추가하면 각 역할의 효과와 비용을 구분하기 쉽다.
