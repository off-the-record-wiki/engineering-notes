# Claude Code - Stop asking, start harnessing

#### 같은 요청 그리고 같은 결과

![](https://github.com/user-attachments/assets/8fdb769f-d8ed-4bd2-9e58-2295d90a2783)

* 어제 잘 통하던 프롬프트가 오늘은 그대로 보내도 다른 파일을 수정할 수도 있고 원하는 방식으로 동작하지 않을 수 있다. 너무 많이 겪었던 부분이다.
* 심각하면 규칙도 어기는 경우가 다반사였다. 왜냐하면 모델은 확률적으로 동작하기 때문이다. 100% 똑같은 동작을 보장한다라는 관점은 LLM 및 AI 서비스에서 불가능하다.
* 모델은 자기 선호 편향이 있어 가지 결과를 좋게 평가한다.

#### 하네스 : 모델의 영역 밖에서 통제를 걸 수 있는 층

![](https://github.com/user-attachments/assets/f1d88d71-8234-4fb6-b889-c778fbe551a0)

* 익히 알고 있던 부분이다. 바로 하네스 엔지니어링. 실제 진행하고 있는 대다수 프로젝트에서 꾸려서 진행을 하고 있다.
* Hooks : 도구 실행 직전에 정해 둔 명령어를 돌린다. 대표적으로 `PreToolUse Hook`은 파일을 고치거나 무언가 명령을 실행하기 직전에 검사하는 과정을 자동화한다.
* Permissions : 특정 명령어 자체를 사용하지 못하게 에이전트의 권한을 설정할 수 있다.
* Sandbox : 에이전트의 작업 범위를 지정하여 운영체제 수준에서의 권한을 제어한다.

#### 토큰은 어디서 발생하는가?

![](https://github.com/user-attachments/assets/355f98cb-473d-4f74-add5-142bc539e762)

* 하네스가 매번 좋은 것은 아니다. 하네스를 추가하면 추가할수록 요청이 늘어나고 그에 따라 비용이 늘어난다.
* 이 토큰에 대한 사용량은 한 번의 요청에 실리는 항목의 크기로 정해지는 것이고 System Prompt와 Tools, CLAUDE.md와 같은 지침 파일들이 하나의 대화 이력에 요청마다 함께 실려간다.
* 이 각각의 항목을 줄이는 방법은 그래서 다르다. 프롬프트 캐싱 관점으로 접근할 수 있고 그에 따라서 지침 파일은 왜 유지해야 하는지도 알 수 있게 된다.
* 하지만 Message라는 컨텍스트 영역은 꽤나 리스크가 있다. 가장 무난하게 빨리 영역을 차지하는 자원이기 때문이다.
