# Claude Code - Design Patterns for Quality-Assured AI Agents

#### 기획과 개발과의 관계를 기반으로 수정 범위를 제한하는 요청서 양식 프롬프트

* 모호한 요청이 만드는 문제 : "페이지를 보기 좋게 만들어 줘"와 같이 기준이 불분명한 요청을 받으면 AI는 빈자리를 스스로 판단해 채운다. 그 결과 색상이나 여백뿐 아니라 차트처럼 요청하지 않은 부분까지 수정될 수 있다.
* 명확한 요청과 상호작용 : 우선순위 기준이 애매하면 먼저 질문해 달라고 요청하면 AI가 필요한 정보를 확인하여 작업할 수 있다. 다만 기준이 이미 분명한 작업에서는 불필요한 질문이 생겨 효율이 떨어진다.
* 좋은 요청의 조건과 지침의 차이 : 좋은 요청에는 대상, 내용, 건드리지 않을 부분, 애매할 때의 처리 방식이 포함된다. 지침(Guideline)은 매번 적용되는 배경 규칙이고, 요청(Request)은 특정 작업 하나에 적용되는 조건이다.
* 요청서 양식 패턴 적용 : 매번 조건을 직접 작성하는 대신 `요청서 양식.md`와 같은 파일에 대상, 내용, 하지 않을 것, 애매한 경우를 담아 템플릿으로 활용한다. 양식에 맞춰 요청하면 수정 범위를 제한해 더 안정적으로 작업할 수 있다.
* 결과 확인 : 요청서로 지정한 범위를 지키도록 유도할 수 있지만 실제 결과를 확인하기 전까지 완벽히 예측할 수 없다.

#### plan mode를 통해 판단, 승인, 작업 3단계에 대한 프로세스 영역 나누기

* 판단·승인·작업 단계의 분리 : 기존 방식은 판단과 작업이 거의 동시에 이뤄져 실행 결과를 예측하기 어렵다. plan mode는 작업 전에 계획을 제시하고 승인을 받게 해 통제력이 높다.
* 플랜 모드 활성화와 작동 방식 : `Shift + Tab`으로 플랜 모드를 켜거나 세션 시작 시 터미널 옵션으로 활성화할 수 있다. 이 모드에서는 파일을 읽고 탐색하되 수정하거나 새로 만들지는 않고 작업 계획을 제시한 뒤 승인을 요청한다.
* 계획 검토와 프롬프트 조정 : 계획 범위가 예상보다 넓으면 `ESC`로 취소하고 요청을 더 구체적으로 좁혀야 한다. 계획을 검토하지 않고 바로 진행하면 플랜 모드를 사용하는 의미가 줄어들기 때문에 동작 관점을 살펴보고 승인하는 과정이 필요하다.
* 플랜 모드의 활용 시기와 `CLAUDE.md` 규칙화 : 간단하고 되돌리기 쉬운 수정에는 매번 계획을 세우지 않아도 된다. 여러 파일을 함께 수정하거나 파일 구조를 바꾸는 큰 작업에 플랜 모드를 활용하고, 그 기준을 `CLAUDE.md`의 공통 규칙으로 정해 일관되게 적용할 수 있다.
* 승인 후 작업 단위 점검 : 계획을 승인해도 결과가 항상 안전한 것은 아니다. 한 계획에 작업이 지나치게 많이 포함되지 않도록 작업 단위를 적절히 나누는 관점이 필요하다.

#### 큰 범위의 작업보다는 단위를 나눔으로써 실패 범위 리스크 조율과 결과물 관리하기

* 여러 작업을 한 번에 요청할 때의 문제 : 한 프롬프트에 여러 작업을 몰아서 요청하면 AI 에이전트가 자체적으로 우선순위를 판단해 처리한다. 그 결과 원하는 작업이 빠지거나 결과를 확인하기 어려워질 수 있다.
* 작업이 많을 때 처리 리스크 증가 : 작업이 많아질수록 앞쪽 항목에 더 큰 비중이 실리고 뒤쪽 항목은 소홀해질 수 있다. 여러 작업을 한 덩어리로 승인하면 오류가 났을 때 되돌려야 하는 범위도 커진다.
* 작업 단위를 나누는 기준 : 되돌렸을 때 손해가 적고 결과를 바로 확인할 수 있으며, 서로 영향을 주는 부분이 겹치지 않도록 작업을 나누는 것이 좋다.
* 체크박스 Task 목록으로 작업 관리하기 : `작업 목록.md`에 남은 일을 체크박스로 정리하고 하나씩 완료할 때마다 표시하면 작업 진행 상황을 명확히 파악할 수 있다. 이런 목록은 AI 에이전트의 비결정적인 작업 진행을 줄이는 데 도움이 된다.
* 작업 분할 : 요청 크기를 조절하고 승인 규칙과 Task 목록을 활용하는 것이 AI 에이전트 작업 관리의 핵심이다.
