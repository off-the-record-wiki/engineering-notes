# gRPC - gRPC Optimization Techniques and Advanced Features

#### gRPC Performance Best Practice - 스텁과 채널 재사용 최적화 패턴

* 채널 : 클라이언트와 서버 사이의 연결 추상화. gRPC에서는 HTTP/2 커넥션을 감싸고 있고, 다음을 관리한다.
  * 대상 주소와 보안 설정
  * 커넥션 풀링, 재연결, 로드밸런싱, 재시도와 같은 정책
  * 연결 상태(`IDLE` → `CONNECTING` → `READY` → `TRANSIENT_FAILURE` → `SHUTDOWN`)
* 생성 비용이 비싸고 thread-safe하므로 앱 수명 주기 동안 하나 만들어 재사용하는 게 원칙이다.
* 요청마다 만들게 된다면 핸드셰이크 비용이 그대로 누적된다.
* 스텁 : `.proto` 정의로부터 생성된 클라이언트 측 대리 객체이다. 원격 호출을 로컬 메서드 호출처럼 보이게 만들어준다.

![](https://raw.githubusercontent.com/wiki/thought-corner/study/images/attachments/c5649a44-9a5b-43b3-b3c1-3fe7f6c1d8c3.png)

* 채널은 TCP와 TLS 핸드셰이크를 포함한 HTTP/2 커넥션을 감싸고 있어 생성 비용이 비싸므로, 애플리케이션 수명 동안 하나만 만들어 모든 스레드가 공유해야 한다.
* 스텁은 직렬화와 메서드 경로 변환만 담당하는 얇은 프록시라 생성 비용이 거의 없지만, 핫 패스에서의 불필요한 할당을 막기 위해 서비스마다 한 번 만들어 캐시해두는 것이 정석이다.
* 이렇게 재사용하면 핸드셰이크가 요청 수만큼이 아니라 기동 시 한 번으로 줄고, HTTP/2 스트림 다중화 덕분에 하나의 연결 위에서 동시 요청이 처리되며, 소켓 TIME_WAIT 누적과 포트 고갈도 사라진다.
* 다만 채널을 오래 살려두면 유휴 연결이 조용히 끊기는 문제가 새로 생기므로, keepalive ping과 호출별 deadline, 재시도 정책, 종료 시 graceful shutdown을 반드시 함께 설정해야 한다.
* 단일 채널은 보통 연결 하나로 수렴해 HTTP/2 동시 스트림 상한에 걸릴 수 있으니, 초당 수천 건 규모나 장시간 스트리밍이 많은 환경에서는 채널 2~4개를 풀로 두고 라운드로빈하는 방식으로 확장한다.

#### gRPC Performance Best Practice - Keep-Alive 핑 메커니즘과 연결 유지

![](https://raw.githubusercontent.com/wiki/thought-corner/study/images/attachments/7a11f6cc-50d4-4e30-a9b3-38f1978e782c.png)

* Keep-Alive 핑은 유휴 시간이 keepalive_time에 도달하면 채널이 HTTP/2 PING 프레임을 보내고 서버가 같은 페이로드로 ACK를 반향하는 아주 가벼운 왕복으로, 이 트래픽이 중간 NAT와 LB의 유휴 타이머까지 함께 초기화해 연결이 조용히 폐기되는 것을 막는다.
* 핑의 두 번째 역할은 죽은 연결을 빠르게 드러내는 것인데, 중간 장비가 연결을 버릴 때 FIN이나 RST가 클라이언트까지 도달하지 않는 경우가 많아 핑이 없으면 채널은 끊긴 연결을 READY로 착각한 채 다음 요청이 타임아웃될 때까지 아무것도 모른다.
* keepalive_timeout 안에 ACK가 오지 않으면 채널은 연결이 끊긴 것으로 판정해 진행 중이던 RPC를 모두 `UNAVAILABLE`로 실패시키고 `READY`에서 `TRANSIENT_FAILURE`를 거쳐 `CONNECTING`으로 전이한 뒤 지수 백오프로 재연결하며, 이때 wait_for_ready로 호출한 RPC는 실패하지 않고 대기하다 복구된 연결에서 그대로 재개된다.
* 핑은 공짜가 아니라서 서버는 허용 최소 간격(min_ping_interval)을 두고 그보다 잦은 핑에는 `GOAWAY`와 `ENHANCE_YOUR_CALM`으로 연결을 강제 종료하므로, 클라이언트의 keepalive_time은 반드시 서버 정책보다 길게 맞춰야 하고 진행 중인 RPC가 없을 때도 보내려면 permit_without_calls를 양쪽에서 함께 허용해야 한다.
* keepalive_time을 경로상 가장 짧은 유휴 타임아웃(흔히 LB의 60초 전후)보다 짧게, keepalive_timeout은 왕복 지연에 여유를 더한 수 초 수준으로 잡되, 값을 무작정 줄이면 서버 부하와 오탐 끊김이 늘어나므로 감지 속도와 비용 사이의 균형점으로 보는 것이 좋다.

#### gRPC Performance Best Practice - 채널 동시성 제한과 채널 풀 해결책

* 채널을 재사용하라는 원칙에는 숨은 함정이 있는데, 채널 하나는 보통 서버당 커넥션 하나로 수렴하고 그 커넥션은 `MAX_CONCURRENT_STREAMS`(서버 기본값이 흔히 100 내외)만큼만 동시 스트림을 열 수 있어서, 이 값을 넘는 요청은 전송되지 못하고 클라이언트 큐에서 순서를 기다린다.
* 이 병목의 특징은 에러가 아니라 지연으로만 드러난다는 점이어서, CPU도 네트워크 대역도 여유로운데 RPS는 천장에 붙고 p99만 치솟는다면 서버 용량이 아니라 채널의 스트림 상한을 먼저 의심해야 한다.
* 커넥션이 하나라는 사실은 부하 분산에도 영향을 주는데, 모든 트래픽이 소켓 하나와 그 소켓을 처리하는 코어 하나를 통과하고 L4 로드밸런서 환경에서는 커넥션 단위로 분배가 일어나므로 뒤에 서버가 열 대 있어도 실제로는 한 대에만 쏠리게 된다.
* 해결책인 채널 풀은 같은 대상 주소로 채널을 여러 개 만들어 요청을 라운드로빈으로 나눠 보내는 방식이며, 동시 스트림 용량이 N배가 되는 동시에 커넥션이 N개로 늘어나 소켓과 코어, 그리고 L4 로드밸런서의 분배까지 함께 개선된다. 이때 채널마다 옵션을 미세하게 다르게 주어야 구현체가 커넥션을 재활용해 다시 하나로 합쳐버리는 것을 막을 수 있고, 스텁도 채널별로 캐시해 채널과 함께 순환시켜야 한다.
* 다만 풀 크기는 무작정 키울 대상이 아니라 보통 2~4개, 많아도 코어 수 이하로 잡는 것이 안전한데, 채널이 늘어날수록 핸드셰이크와 keepalive 핑, 서버 측 커넥션 관리 비용이 비례해 늘기 때문이다. 순서로 보면 채널·스텁 재사용 → 지표로 스트림 상한 확인 → 서버 측 상한 조정이나 L7 로드밸런싱 검토 → 그래도 부족할 때 채널 풀이 합리적인 접근이다.

#### 통신 안정화를 위한 Flow Control과 코드 재사용을 위한 Interceptors - Flow Control 기본 메커니즘

![](https://raw.githubusercontent.com/wiki/thought-corner/study/images/attachments/649f34ed-46bc-4dc5-a2b4-d4cc5a3546c0.png)

* Flow Control은 송신자가 마음대로 데이터를 밀어 넣지 못하게 막는 크레딧 방식의 신용 한도로, 수신자가 허락한 바이트 수(윈도우)만큼만 보낼 수 있고 보낸 만큼 윈도우가 깎이며 수신 애플리케이션이 실제로 데이터를 소비한 뒤 `WINDOW_UPDATE` 프레임으로 그만큼을 돌려줘야 다시 전송이 가능해진다.
* 여기서 핵심은 윈도우를 돌려주는 주체가 네트워크가 아니라 수신 애플리케이션의 소비 속도라는 점인데, 그래서 소비자가 느려지면 `WINDOW_UPDATE`가 늦게 오고 윈도우가 0에 도달하면 송신 측이 스스로 전송을 멈추며, 이 압력이 소켓을 거쳐 송신 애플리케이션의 write 블로킹이나 `is_ready = false` 신호까지 역류한다. 이것이 백프레셔이고, 버퍼를 무한정 쌓다 OOM으로 죽는 대신 생산 속도를 소비 속도에 맞춰 늦추는 안전장치다.
* 윈도우는 스트림 단위와 커넥션 단위 두 층으로 동시에 적용되어, 한 번의 전송은 두 윈도우를 모두 깎고 둘 중 하나라도 0이면 멈춘다. 따라서 대용량 스트리밍 RPC 하나가 커넥션 윈도우를 고갈시키면 같은 채널을 공유하는 다른 RPC까지 함께 멈추는데, 이는 채널 재사용의 대가이며 무거운 스트리밍은 전용 채널로 분리하는 것이 정석이다.
* 기본 윈도우(HTTP/2 표준 초기값 64KB)는 대역폭-지연 곱이 큰 환경에서 금방 병목이 되므로, 장거리·고대역폭 링크에서 처리량이 안 나올 때는 윈도우 크기를 키우거나 BDP 기반 자동 튜닝을 켜는 것이 우선 검토 대상이다. 다만 윈도우를 키운다는 것은 곧 메모리 버퍼를 키운다는 뜻이라 처리량과 메모리 사용량의 교환이라는 점을 잊지 않아야 한다.
* Flow Control이 과부하를 막아주지는 않는다는 것인데, 이것은 어디까지나 전송 속도를 맞춰주는 장치이고 요청 수 자체를 제한하는 동시성 상한이나 속도 제한, 그리고 호출별 deadline은 별도로 설정해야 한다.

#### 통신 안정화를 위한 Flow Control과 코드 재사용을 위한 Interceptors - 백프레셔와 윈도우 업데이트 메커니즘

![](https://raw.githubusercontent.com/wiki/thought-corner/study/images/attachments/e7422f4c-756a-4caa-9b3f-4de411f48130.png)

* 윈도우는 수신자가 송신자에게 미리 내준 신용 한도이며, 송신자는 DATA를 보낼 때마다 보낸 바이트 수만큼 잔량을 깎고 잔량이 0이 되는 순간 더 보낼 프레임이 남아 있어도 스스로 전송을 멈춘다. 이 정지는 에러가 아니라 정상 동작이며, 재전송이나 폐기 없이 그저 기다린다.
* `WINDOW_UPDATE`를 촉발하는 것은 데이터가 도착한 시점이 아니라 수신 애플리케이션이 실제로 읽어간 시점인데, 이 한 가지 사실이 백프레셔 전체를 설명한다. 소비가 늦으면 반환이 늦고, 반환이 늦으면 송신 윈도우가 마르고, 그 압력이 소켓을 거쳐 송신 애플리케이션의 write 블로킹이나 `is_ready = false`로 되돌아온다.
* 그래서 백프레셔를 실제로 누리려면 애플리케이션이 소비 신호를 정직하게 내보내야 한다. 받은 메시지를 곧바로 내부 큐에 옮겨 담고 바로 다음 메시지를 요청하는 코드는 프레임워크 입장에서 "빨리 소비 중"으로 보이므로 윈도우가 계속 반환되고, 결국 압력은 전달되지 않은 채 애플리케이션 메모리에만 쌓여 OOM으로 끝난다. 비동기 스트리밍의 request(n)이나 onReadyHandler, 동기 스트리밍의 블로킹 이터레이터가 이 신호를 다루는 지점이다.
* 윈도우 갱신은 스트림 단위와 커넥션 단위가 별도로 집계되어, 한 번의 전송이 두 계정을 동시에 깎고 두 계정에 각각 WINDOW_UPDATE가 돌아온다. 스트림 윈도우가 넉넉해도 커넥션 윈도우가 마르면 같은 채널의 모든 RPC가 함께 멈추므로, 증상이 특정 RPC가 아니라 채널 전체에 걸쳐 나타난다면 커넥션 레벨 고갈을 의심해야 한다.
* 윈도우 크기를 키우면 대역폭-지연 곱이 큰 링크에서 처리량이 올라가지만 그만큼 버퍼 메모리를 더 쓰고 압력이 늦게 전달된다는 부작용이 따른다. 즉 큰 윈도우는 처리량을, 작은 윈도우는 빠른 백프레셔와 낮은 메모리를 택하는 교환이며, 어느 쪽이든 죽은 연결 방어(keepalive)나 무한 대기 방지(deadline)는 Flow Control이 대신해주지 않으므로 별도로 설정해야 한다.

#### 통신 안정화를 위한 Flow Control과 코드 재사용을 위한 Interceptors - gRPC 데이터 전송 생명주기

![](https://raw.githubusercontent.com/wiki/thought-corner/study/images/attachments/87459546-4c99-41ee-8608-430b8ef13aba.png)

* RPC 한 건은 HTTP/2 스트림 하나의 수명과 정확히 일치하며, HEADERS 프레임으로 시작해 하나 이상의 DATA 프레임을 거쳐 TRAILERS 프레임으로 끝난다. 이 구조 덕분에 하나의 연결 위에서 수많은 RPC가 각자의 스트림으로 독립적으로 살고 죽을 수 있다.
* 나가는 길의 변환은 직렬화 → 압축 → 프레이밍 순서로 일어나는데, protobuf로 바이트가 된 메시지 앞에 `[1바이트 압축 플래그][4바이트 길이]`의 5바이트 프리픽스가 붙는다. 이 프리픽스가 있어 수신 측은 TCP 스트림에서 메시지 경계를 정확히 잘라낼 수 있고, 하나의 DATA 프레임에 여러 메시지가 실리거나 반대로 한 메시지가 여러 프레임에 쪼개져도 문제가 없다.
* 인터셉터는 이 파이프라인의 양 끝에 붙는 훅으로, 클라이언트 쪽에서는 직렬화 직전에 토큰 부착·로깅·메트릭 시작을 처리하고 서버 쪽에서는 역직렬화 직후 핸들러 진입 전에 인증 검증과 예외 변환을 처리한다. 즉 인터셉터가 다루는 것은 바이트가 아니라 메시지와 메타데이터이며, 응답 경로에서는 체인을 역순으로 통과한다.
* gRPC의 가장 특징적인 지점은 최종 상태가 헤더가 아니라 트레일러로 온다는 것인데, 응답 HEADERS의 :status 200은 HTTP 수준의 성공일 뿐이고 실제 RPC 성공/실패는 마지막 TRAILERS의 grpc-status로 결정된다. 서버가 스트리밍 도중 실패하는 경우를 표현하려면 상태를 끝에 실어야 하기 때문이며, 그래서 200 OK를 받고도 RPC가 실패할 수 있다.
* Flow Control이 개입하는 구간은 오직 DATA 프레임 전송 구간 하나이고, HEADERS와 TRAILERS는 윈도우를 소모하지 않는다. 따라서 "요청은 시작됐는데 진전이 없다"는 증상은 대개 이 DATA 구간의 윈도우 고갈이며, deadline이 만료되거나 호출이 취소되면 TRAILERS 대신 RST_STREAM이 나가 해당 스트림만 정리되고 채널과 TCP 연결은 그대로 유지돼 다른 RPC는 영향을 받지 않는다.

#### 통신 안정화를 위한 Flow Control과 코드 재사용을 위한 Interceptors - 인터셉터 패턴과 공통 기능 처리

![](https://raw.githubusercontent.com/wiki/thought-corner/study/images/attachments/343b3b00-cd24-44af-b873-4e35fc5c0f02.png)

* 인터셉터는 모든 RPC가 반드시 통과하는 중첩된 껍질로, 각 껍질은 요청을 받아 원하는 일을 한 뒤 안쪽 껍질을 호출하고 그 결과를 받아 다시 바깥으로 돌려준다. 이 구조 덕분에 인증·로깅·재시도 같은 횡단 관심사가 서비스 핸들러 코드에서 완전히 사라지고, 껍질 하나를 갈아 끼우면 전체 RPC에 한 번에 적용된다.
* 통과 방향이 요청과 응답에서 반대라는 점이 실무의 핵심인데, 등록 순서가 곧 바깥 껍질 순서이고 응답은 정확히 역순으로 되돌아오므로 "시작 시각 기록 → 안쪽 호출 → 경과 시간 기록" 같은 코드가 자연스럽게 한 함수 안에 담긴다. 따라서 순서를 잘못 잡으면 기능이 조용히 무력화되는데, 예컨대 인증을 로깅보다 바깥에 두면 인증 실패 요청이 로그에 남지 않는다.
* 클라이언트와 서버는 책임이 대칭이 아니라 상보적이다. 클라이언트 쪽 껍질은 토큰 부착, 지연 측정, 재시도와 서킷 브레이커처럼 "보내기 전과 실패 후"를 다루고, 서버 쪽 껍질은 인증 검증, 속도 제한, 예외를 상태 코드로 바꾸는 일처럼 "받은 뒤와 응답 직전"을 다룬다. 같은 로깅이라도 양쪽에 두는 이유는 네트워크 구간을 사이에 둔 두 관점이 서로 다르기 때문이다.
* 메타데이터는 인터셉터가 다루는 주 통신 수단인데, 요청 헤더에 토큰과 트레이스 ID를 싣고 응답 트레일러에서 상태를 읽는 식이다. 인터셉터는 바이트가 아니라 메시지와 메타데이터를 보므로, 직렬화 이전과 역직렬화 이후라는 위치가 이 패턴이 성립하는 전제가 된다.
* 다만 단항 호출과 스트리밍 호출은 인터셉터 작성 방식이 다르다는 점에 주의해야 한다. 단항은 요청과 응답이 각각 하나라 "앞뒤를 감싸는" 코드로 충분하지만, 스트리밍은 메시지가 계속 흐르므로 호출 스트림 객체를 감싸 각 메시지마다 훅이 돌게 만들어야 하고, 여기서 무거운 작업을 하면 메시지마다 비용이 곱해져 그대로 처리량 저하로 이어진다. 재시도 인터셉터를 직접 구현할 때도 멱등성이 보장되는 메서드에만 적용해야 한다.

#### gRPC Load Balancing과 Reflection

* 리플렉션 서비스는 이 서버에 어떤 API가 있는지 서버한테 직접 물어보는 기능이다.
* 원래 gRPC는 클라이언트가 `.proto` 파일을 미리 가지고 있어야 호출할 수 있다. 리플렉션을 켜면 서버가 자기 스키마를 응답으로 내주기 때문에 `.proto` 없이도 호출할 수 있게 된다. API 전체 구조가 드러나기 때문에 개발·스테이징에서만 켜고 프로덕션에서는 끈다.

#### Graceful Shutdown을 통한 리소스 정리 & Request Hedging을 통한 최적화

![](https://raw.githubusercontent.com/wiki/thought-corner/study/images/attachments/d35027e4-c295-4137-804f-42071cdca71d.png)

* 우아한 종료의 정의는 단순한데, 새로 들어오는 요청은 받지 않으면서 이미 받은 요청은 끝까지 처리하고 내려가는 것이다. 반대로 프로세스를 즉시 죽이면 처리 중이던 RPC가 모두 `UNAVAILABLE로`로 끊기고, 그 실패는 재시도할 수 없는 쓰기 작업이었다면 그대로 데이터 불일치로 남는다.
* 이를 가능하게 하는 것이 HTTP/2의 `GOAWAY` 프레임인데, 서버가 "이 연결로는 더 이상 새 스트림을 받지 않겠다"는 뜻을 클라이언트에 알리면서 이미 열린 스트림은 계속 살려두기 때문이다. 클라이언트는 이 신호를 받고 진행 중인 RPC는 그대로 끝내고 새 호출만 다른 서브채널이나 새 연결로 보내며, 애플리케이션 코드는 아무것도 하지 않아도 된다.

![](https://raw.githubusercontent.com/wiki/thought-corner/study/images/attachments/a1029e69-a041-41b4-8270-c8f20193b2a7.png)

* 헤징은 실패를 기다리지 않는 재시도이다. 일반 재시도가 "실패를 확인한 뒤 다시 보낸다"면, 헤징은 첫 요청을 보낸 뒤 hedgingDelay가 지나도 응답이 없으면 실패 여부와 무관하게 다른 서버로 같은 요청을 한 번 더 보내고, 가장 먼저 도착한 응답을 채택한 뒤 나머지는 즉시 취소한다. 목표는 평균 지연이 아니라 꼬리 지연(p99) 으로, 서버 한 대가 GC나 일시적 부하로 느려진 상황에서 그 한 건이 전체 지연을 끌어올리는 것을 막는다.
* 대가는 명확한데, 헤징은 같은 요청을 여러 번 실행시키므로 부하가 시도 횟수만큼 곱해진다. `hedgingDelay`는 정상 응답 시간의 p90~p95 언저리로 잡아 대부분의 요청이 헤지 전에 끝나게 해야 하고, 이 값을 너무 짧게 잡으면 거의 모든 요청이 두세 번씩 나가 서버를 스스로 무너뜨린다.
* 멱등성이 전제 조건이라는 점도 중요하다. 헤징은 취소된 요청이 서버에서 이미 처리됐을 수 있으므로 조회처럼 여러 번 실행돼도 안전한 메서드에만 적용해야 하며, 결제나 생성처럼 부작용이 있는 호출에 켜면 중복 실행이 발생한다. 참고로 gRPC의 서비스 설정에서 재시도와 헤징은 메서드당 택일이며 동시에 지정할 수 없다.
* Pushback은 서버가 직접 클라이언트를 제어하는 장치로 응답 트레일러에 `grpc-retry-pushback-ms`를 실어 보내면 클라이언트는 설정된 백오프 대신 서버가 지정한 시간만큼 기다렸다 재시도하고, 값이 음수면 재시도를 아예 포기한다. 과부하 상태의 서버가 "지금은 오지 마라"를 직접 말할 수 있다는 뜻이어서, 클라이언트 측 추정에만 의존하는 백오프보다 훨씬 정확하게 부하를 조절한다.
