# Kubernetes - What to Know Before You Deploy

#### Kubernetes - CI/CD 파이프라인을 구성할 때 고려해야 하는 요소

* CI는 코드가 저장소에 반영될 때 빌드와 테스트를 자동으로 실행하여 코드가 정상적으로 통합되는지 검증하는 과정이다.
* CD는 CI를 통과한 결과물을 개발·스테이징·운영 환경에 전달하거나 자동 배포하는 과정이다.
* 일반적인 파이프라인은 코드 Push → 빌드 → 테스트 → 정적 분석 → Artifact 생성 → 배포 → 상태 확인 순서로 진행된다.
* 동일한 소스는 동일한 결과물로 빌드되어야 하며, 운영 환경에서 코드를 다시 빌드하지 않고 CI에서 검증한 Artifact를 그대로 배포해야 한다.
* 데이터베이스 주소, API Key, 비밀번호 같은 환경별 설정과 Secret은 소스 코드 및 컨테이너 이미지에 포함하지 않아야 한다.
* 배포 시에는 Rolling, Blue-Green, Canary 같은 전략의 차이를 이해하고, 장애가 발생하면 이전 버전으로 롤백할 수 있어야 한다.
* DB 스키마 변경은 이전 애플리케이션 버전과 호환되도록 설계하고, 배포 순서와 롤백 가능성을 함께 고려해야 한다.
* 배포 성공 여부는 프로세스 실행만으로 판단하지 않고 Health Check, 로그, 메트릭 및 실제 API 응답으로 확인해야 한다.

#### Kubernetes - 배포 전략을 세울 때 고려해야 하는 요소

* 서비스 중단 허용 여부를 확인하여 배포 중 다운타임이 가능한지, 무중단 배포가 필요한지 결정한다.
* 변경 위험도와 영향 범위를 고려하여 장애 발생 시 일부 사용자만 영향을 받을지 전체 사용자가 영향을 받을지 판단한다.
* 버전 간 호환성을 확인하여 구버전과 신버전이 동시에 실행될 때 API, 메시지 및 캐시 데이터가 정상적으로 처리되는지 검증해야 한다.
* 데이터베이스 변경은 컬럼 삭제나 타입 변경처럼 되돌리기 어려운 작업을 피하고, 애플리케이션 배포 전후 버전이 모두 사용할 수 있도록 단계적으로 수행해야 한다.
* 상태 관리 방식을 점검하여 세션, 로컬 파일, 장시간 실행 작업 및 처리 중인 메시지가 인스턴스 교체 과정에서 유실되지 않게 해야 한다.
* 트래픽 전환 방식을 결정하여 전체 트래픽을 한 번에 옮길지, 비율이나 사용자 그룹에 따라 점진적으로 옮길지 정해야 한다.
* 검증 기준을 미리 정의하여 오류율, 응답 시간, 자원 사용률 및 핵심 비즈니스 지표가 어떤 수준이면 배포를 계속하거나 중단할지 결정해야 한다.
* 롤백 가능성을 확보하여 이전 Artifact와 설정을 보관하고, DB 변경처럼 단순 롤백이 어려운 경우에는 Roll-forward나 Feature Flag 전략을 준비해야 한다.
* 인프라 용량과 비용을 고려하여 구버전과 신버전을 동시에 실행할 여유 자원이 있는지 확인해야 한다.
* 자동화 및 승인 범위를 정하여 배포, 검증, 트래픽 전환, 중단 및 복구 중 어떤 단계를 자동화하고 사람이 승인할지 결정해야 한다.
